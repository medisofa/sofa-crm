Cómo subir una iteración de SOFA

Guía paso a paso, con la Iteración 18 (1.8.0) como ejemplo. Sirve igual para la 19, 20…: cambie el número donde diga 18.

Antes de empezar: 4 diferencias con los comandos originales

Los comandos que acompañan el paquete suponen una estructura que este repositorio no tiene. Si se copian tal cual, fallan o suben cosas al lugar equivocado:

Comando originalQué pasa en este repositorioCorrección en esta guía
git add app/js app/css docsNo existe carpeta app/ ni docs/: el sitio vive en la raíz (js/, css/, index.html). GitHub Pages no serviría nada que quede dentro de app/.Se descomprime en una carpeta aparte y se copia el contenido de app/ a la raíz (paso 3).

Estado actual de la 18 en main: ya hay un commit «Iteración 18 (SOFA 1.8.0)» con solo los 6 archivos nuevos (css/iter18.css, js/modules/statement.js, weekly.js, profitability.js, collections-calendar.js, js/services/iter18.js). Todavía no están conectados al menú (index.html / router.js no los cargan) y js/version.js sigue en 1.7.5. No hay migración de la 18 en supabase/migrations/. Esta guía completa lo que falta.
Repositorio público. medisofa/sofa-crm es público y el propio README dice que los scripts SQL «describen las reglas internas del negocio» y no deben subirse a un repositorio público. Decida antes del paso 5 si las migraciones van aquí (como ya está la 060) o a un repositorio privado. Nunca suba la contraseña de la base, la sb_secret_… ni la service_role.

Lo que necesita

  • Git instalado y el repositorio clonado en su equipo (git clone https://github.com/medisofa/sofa-crm.git).
  • El archivo sofa_iteracion_18.zip (en estos ejemplos, en Descargas).
  • Una terminal: Terminal en Mac, Git Bash en Windows (no CMD).
  • Acceso al SQL Editor del proyecto en Supabase.

Todos los comandos se escriben dentro de la carpeta del repositorio. Ajuste estas dos líneas una vez y péguelas al abrir la terminal:

REPO=~/sofa-crm                              # dónde está su copia del repositorio
ZIP=~/Downloads/sofa_iteracion_18.zip        # el paquete recibido
cd "$REPO"

Pasos

1Partir de un main limpio y actualizado

git status
git checkout main
git pull origin main

git status debe decir nothing to commit, working tree clean. Si muestra archivos modificados, no siga: guárdelos (git stash) o pregunte, porque se mezclarían con la iteración.

2Crear la rama de la iteración

git checkout -b iteracion-18

Nunca se trabaja directo en main: main es lo que publica GitHub Pages. Si la rama ya existe, use git checkout iteracion-18.

3Mirar el paquete y descomprimirlo fuera del repositorio

unzip -l "$ZIP"

Revise la lista: qué carpetas trae (app/, js/, supabase/, docs/) y si aparece algún config.js. Luego:

TMP=$(mktemp -d)
unzip -q "$ZIP" -d "$TMP"
find "$TMP" -name config.js -print -delete      # nunca se copia config.js

# El sitio vive en la raíz: lo que venga dentro de app/ va a la raíz
[ -d "$TMP/app" ]      && cp -R "$TMP/app/." "$REPO/"
[ -d "$TMP/js" ]       && cp -R "$TMP/js/."  "$REPO/js/"
[ -d "$TMP/css" ]      && cp -R "$TMP/css/." "$REPO/css/"
[ -d "$TMP/supabase" ] && cp -R "$TMP/supabase/." "$REPO/supabase/"
# La guía de la iteración, junto a las anteriores (en la raíz)
[ -d "$TMP/docs" ]     && cp "$TMP"/docs/*.html "$REPO/"

ls "$TMP"     # ¿quedó algo que no se copió? (index.html, sw.js…) — revíselo

Si ls muestra archivos sueltos como index.html, sw.js o README.md en la raíz del paquete, cópielos también: cp "$TMP/index.html" "$TMP/sw.js" "$REPO/".

Sin unzip (Windows)

Clic derecho en el zip → Extraer todo… a una carpeta fuera del repositorio. Borre cualquier config.js que aparezca. Luego copie el contenido de app\ a la raíz del repositorio (no la carpeta app misma), supabase\ sobre supabase\, y la guía .html de docs\ a la raíz.

4Verificar antes de confirmar

cd "$REPO"
git diff --quiet -- js/config.js && echo "ok: config.js intacto" || echo "PARA: config.js cambió"
[ -d app ] && echo "PARA: se creó una carpeta app/ (los archivos van en la raíz)" || echo "ok: sin app/"
grep APP_VERSION js/version.js        # debe decir la versión nueva, p. ej. '1.8.0'
git status --short

Si algo dice PARA:

  • config.js cambió → git checkout -- js/config.js (recupera el suyo).
  • Apareció app/ → cp -R app/. . && rm -rf app.

En git status --short, M = modificado y ?? = nuevo. Debe ver solo archivos de la iteración. Para ver qué cambió en uno: git diff js/router.js.

5Confirmar (commit) y subir la rama

git add js css supabase index.html sw.js README.md guia_*.html
git status --short                    # js/config.js NO debe aparecer en verde
git commit -m "Iteración 18 (1.8.0): estado de cuenta con ROI, calendario de cobros, resumen semanal, rentabilidad"
git push -u origin iteracion-18

Si git add dice que alguna ruta no existe (p. ej. README.md no cambió), no pasa nada: quítela del comando. Si el push pide usuario y contraseña, GitHub exige un token o GitHub Desktop; la contraseña normal no funciona.

6Abrir el Pull Request

  1. Entre a github.com/medisofa/sofa-crm. Aparece un aviso amarillo «iteracion-18 had recent pushes» → Compare & pull request.
  2. Base: main ← compare: iteracion-18.
  3. Pestaña Files changed: confirme que js/config.js no está y que no hay carpeta app/.
  4. Create pull request. Todavía no haga merge.

7Base de datos: migración y regresiones

  1. Supabase → SQL Editor → New query.
  2. Pegue la migración nueva de supabase/migrations/ (la de número más alto que trajo el paquete) y Run. Si son varias, en orden de número. Si avisa que falta una migración anterior, aplíquela primero.
  3. Corra la suite de pruebas que acompaña la iteración (supabase/tests/) y las regresiones generales, como indique la guía de la iteración.
  4. Todo en verde → siga. Algo en rojo → no haga merge; copie el resultado completo y envíelo para corregirlo.
Base primero, frontend después: si se publica la pantalla antes de la migración, los usuarios verían errores al abrir los módulos nuevos.

8Merge y comprobación en vivo

  1. En el Pull Request → Merge pull request → Confirm merge.
  2. Pestaña Actions: espere a que «pages build and deployment» quede en verde (1–3 min).
  3. Abra la aplicación y recargue forzando (Ctrl+Shift+R / Cmd+Shift+R): el service worker guarda la versión anterior.
  4. Verifique la versión en el pie o en Diagnóstico y abra cada pantalla nueva una vez.
  5. Limpie en su equipo: git checkout main && git pull origin main && git branch -d iteracion-18.

Si algo sale mal

SituaciónQué hacer
Copié mal y aún no hice commitgit restore . y git clean -fd (borra lo nuevo sin confirmar) → repita desde el paso 3.
Hice commit pero no pushgit reset --soft HEAD~1, corrija, y vuelva al paso 4.
Ya hice push pero no mergeCorrija en la misma rama, git add + git commit + git push: el Pull Request se actualiza solo.
Ya hice merge y la app fallaEn el Pull Request cerrado → Revert → crea otro Pull Request que deshace el cambio → merge. La base de datos no se revierte con esto.
config.js llegó a GitHub con una clave secretaRote la clave en Supabase de inmediato (borrarla del repositorio no basta: queda en el historial).

Lista rápida

  • main limpio y actualizado
  • Rama iteracion-NN creada
  • Paquete revisado con unzip -l y descomprimido fuera del repo
  • config.js intacto, sin carpeta app/, versión nueva en version.js
  • Commit y push de la rama
  • Pull Request abierto y archivos revisados
  • Migración aplicada y regresiones en verde
  • Merge, Pages en verde, recarga forzada y prueba de pantallas
