Gestión de Duplicados

Flujo frontend de resolución · v5.39.0 (solicitar) + v5.41.0 (ejecutar) · noviembre 2026

1 · Flujo general

Cuando el sistema detecta que dos reclamaciones del mismo paciente, mismo procedimiento y misma fecha fueron enviadas a la misma ARS, las marca como duplicado confirmado. A partir de ahí, el equipo puede resolver el duplicado desde el diálogo de resolución.

Duplicado detectado → Revisión (confirmar/descartar) → Solicitar exclusión → Ejecutar exclusión → Reclamación eliminada
Acción irreversible. Una vez ejecutada la exclusión, la reclamación se elimina del lote. No se puede recuperar desde la interfaz. Los archivos del Storage asociados a la reclamación eliminada no se borran automáticamente (pendiente conocido).

Modo soporte. Cuando viewAs está activo (un admin está viendo como otro rol), las acciones de solicitar y ejecutar exclusión se deshabilitan. Solo se permite «Corregir».

3 · Las tres acciones del diálogo

3.1 · Corregir

Navega al editor de la reclamación (#/reclamaciones/{id}) para que el usuario corrija los datos que causaron el duplicado. Disponible para REQUEST_ROLES.

3.2 · Solicitar exclusión

Crea una solicitud de exclusión para que un administrador la revise y ejecute.

Validaciones previas (frontend)

  • El par de reclamaciones debe tener un bloqueo confirmado activo (campo confirmed_block).
  • No debe existir ya una solicitud pendiente para ese par.
  • El motivo debe tener al menos 10 caracteres.
  • El usuario debe seleccionar cuál reclamación conservar (keepLine).

3.3 · Ejecutar exclusión

Solo disponible cuando existe una solicitud pendiente. El administrador confirma y la reclamación descartada se elimina del lote.

Validaciones previas (frontend + backend)

  • Debe existir una solicitud de exclusión en estado pendiente.
  • Solo roles EXECUTE_ROLES (admin, super_admin).
  • El modo soporte (viewAs) bloquea esta acción.
  • El backend verifica internamente: lote editable, sin pagos, sin glosas, sin reenvíos.
  • Solo reclamaciones en estados de captura: pendiente_configuracion, capturada, pendiente_retiro.
Diálogo de confirmación destructiva. Antes de ejecutar, el sistema muestra un confirmDialog con el texto: «Esta acción eliminará la reclamación del lote y no se puede deshacer.»

Siete funciones respaldan el flujo. Las marcadas DEFINER se ejecutan con permisos del propietario de la función; las marcadas INVOKER respetan la RLS del usuario que llama.

6 · SQL — Consultas de verificación

6.1 · Ver solicitudes de exclusión pendientes

SELECT r.id, r.created_at, r.reason, r.status,
       la.folio AS folio_a, lb.folio AS folio_b,
       lk.folio AS folio_conservada
FROM   claim_duplicate_resolution_requests r
JOIN   claim_service_lines la ON la.id = r.line_a
JOIN   claim_service_lines lb ON lb.id = r.line_b
JOIN   claim_service_lines lk ON lk.id = r.keep_line
WHERE  r.status = 'pendiente'
ORDER BY r.created_at DESC
LIMIT 20;

6.2 · Ver bloqueos de duplicados confirmados

SELECT d.id, d.line_a, d.line_b, d.decision,
       d.confirmed_block, d.created_at
FROM   claim_duplicates d
WHERE  d.confirmed_block = true
  AND  d.decision = 'confirmed'
ORDER BY d.created_at DESC
LIMIT 20;

6.3 · Verificar que una reclamación fue eliminada

-- Buscar en el log de auditoría
SELECT al.created_at, al.action, al.details,
       al.performed_by
FROM   audit_log al
WHERE  al.action LIKE '%remove_service_line%'
ORDER BY al.created_at DESC
LIMIT 10;
